# Agent Plan control and Runner synchronization (PAGE-184 / PAGE-185)

This source change requires Pages plan contract **13**, migration **084**, and
Runner **1.15.0**, with authenticated `planControlVersion: 1`. It does not
establish production rollout or acceptance. The assignment's separate operational
report records the tested tree, real executions and outstanding proofs.

## Confirmed causes

The historical Pica_Mobile NAS run
`3eaec26d-3c01-44c3-86fb-6eac5b6f46f4` returned a blocked business result after
an unsuccessful Pages ticket/checklist request. Codex/Claude standalone completion

`bc054de8-f581-4a28-b4e1-8f49510fcbdd`, job
`84ef6eca-9111-4fec-9af2-536fbffcf26f`, had no proved process launch. Missing launch
files are not proof that an arbitrary historical process never existed.

The separate current Runner 1.14.0 disconnect has a concrete schema cause: its
reconciliation sends four tools (Codex, Claude, OpenCode and Antigravity), but the
legacy reconciliation `tools` field allowed three. The atomic catalog already
allowed four. Both fields now accept the supported four-tool inventory. Protocol
rejections log bounded field paths, codes and expected types, without values.
Transport close diagnostics include connection/session, stage and a bounded cause.
Neither HTTP health nor supervisor status establishes authenticated synchronization.

## Business completion and access

Every local or remote CLI needs accepted business work before success-dependent
successors and immutable success checkpoints. Technical exit, output, business
acceptance and process closeout remain separate facts. Structured blocked, open,
incomplete or failed results cannot release successors, including API model
results. Earlier technically successful CLI results with an open acceptance are
retried at that incomplete step during continuation.

Local and remote capabilities use the same scope builder. Ticket-only access
lists the bound operations and tickets explicitly; read/full access still follows
the executor's live permissions. No provider login or blanket privilege is added.
Remote capabilities survive queue time, are checked on each request, close with
the attempt, and are reissued only for exact still-active owned jobs after Pages
restart, with old credentials revoked. A denied historical content read does not
grant that content through control-only reset or cancellation.

Native remote Codex marks the supplied Pages MCP server as required and waits up
to 30 seconds for startup, matching the local Codex ACP startup wait. Optional
MCP startup can otherwise omit a slow tool catalog from the first turn without
an initialization error. A failed required bridge must stop startup instead of
letting the agent work without its authorized tools. This changes only the
per-job invocation; it grants no additional access and changes no host settings.
Deliver the patched Runner module even when its installed version already says
1.15.0: compare the final source/module hashes, not only the version string.

## Upper controls

- Start begins the saved revision. For an existing own run, its confirmation
  belongs to this upper action, including active, paused, failed and stopping runs.
- Pause drains running work. Resume continues the durable paused frontier.
- Failed/interrupted/business-blocked runs offer a separate Resume decision.
  Verified successful predecessors are retained. Local native sessions are used
  only with recorded adapter support; replacement sessions receive an explicit
  context-change notice and retained prior business context. Complete history and
  checkpoints remain stored; bounded output excerpts are labelled as excerpts.
- An explicit Stop is durable, works while paused, prevents successors and removes
  Resume for that run after reload/reconnect. A server interruption is distinct.
- A confirmed fresh start atomically retires only its own predecessor. It preserves
  old resource ownership and jobs, and queues conflicting new work behind them.
  When current configuration prevents a new run, `outcome: reset` restores logical
  control, retains cleanup obligations and reports the configuration issue without
  starting a process. It does not claim physical cleanup.

There is no separate recovery/release panel in the regular UI. Diagnostics remain.
Previously started scripts require a concrete effect review in the chosen action,
including files, preparation, commit/push and external results. Continuation does
not silently replay successful predecessors. Fresh execution never resets files,
branches, authentication or history on behalf of the control layer.

Commands keep revision guards and durable idempotency receipts. The UI retains the
exact request identity/revision across uncertain transport retries. A rejected
progress-only revision can refresh once within the chosen action; changed saved
plan revisions still require a new decision. Late facts for old attempts and
settled jobs retain custody/acknowledgement without regressing terminal execution.
History import no longer blocks the channel's control queue.

## Actual writer coordination

Referencing a workspace registration does not reserve it. Read-only CLI and API
model steps do not take Pages writing leases; Runner admission allows independent
readers of the same registration. Actual writable local canonical directories and
remote host/path resources are coordinated. Colliding writers queue as usable
runs instead of refusing their plan, retaining exact owner/attempt evidence and
an actionable blocker. They wake again after reconciliation. Existing legacy
leases are matched to their actual snapshot resources, never silently discarded.

This implementation coordinates actual resources; it does not create per-run
repository copies. Two writers using the same actual working tree are serialized
for the workflow to protect preparation/agent/closeout across steps. Independent
readers or plans using distinct actual writing directories can run concurrently.
Host capacity remains four admitted jobs per account. Unknown legacy ownership
remains a visible safety obligation, not process-free proof or a force unlock.

## Registration deletion and cleanup

Removal stays available in unused, referenced, running, paused, failed, stopping
and offline states. Its transaction removes the active registration, detaches
current plan/template/pinned-agent bindings and fences new dispatch. A removed
remote override remains explicitly missing (`missing-workspace`), so reassigning
the plan default cannot silently turn it into local or another remote execution.
Plans, immutable run/continuation snapshots and journals are retained.

Deleting a registration never recursively deletes the repository or user files.
Pending work is represented by `agent_workspace_cleanup`, with original run,
executor, requesting person, timestamps and current blocker. The original run
retains exact job, attempt, session, connection and launch evidence. The cleanup
service retries only those owners across server restart and Runner reconnect.
Logical deletion never waits for an offline host. Upper control metadata and MCP
`read_plan_control` expose the same own obligations and concrete writer waits;
completed cleanup records remain stored.

Queue cancellation can prove non-launch only by winning the exclusive claim
creation fence and durably sealing `not_started`. Missing ownership records of an
already existing claim remain unknown. Started work uses its recorded namespace
supervisor identity; termination is bounded and belongs only to that exact owner.
Confirmed cleanup cannot be weakened by later stale facts. No DB patch, fabricated
ACK, journal deletion, global kill, force unlock or user-file reset is a repair.

## Rollout requirements (separate authorization required)

1. Review the exact source and validation report. Build Pages and standalone MCP
   together in an isolated staging copy; retain paired previous artifacts and a
   normal runtime backup. Do not build into a serving checkout or `mcp/dist`.
2. Deploy the paired Pages/MCP artifacts and apply migration 084 under the normal
   authorized operational procedure. This assignment performs no production rollout.
3. Deliver Runner 1.15.0 from the same source. Existing older jobs remain readable,
   reconcilable and cancellable. New dispatch requires the new authenticated
   capability; do not bypass it. Wait for owned active work or explicitly arrange
   its stop before any separately authorized Runner restart.
4. Preserve pairing, provider contexts, configuration and job directories. Do not
   repair the old Pica job by deleting or inventing ownership evidence. Verify
   registration, negotiated schema/capability, heartbeat, sequence checkpoints,
   exact job reconciliation and catalog with all four tools.
5. Roll back paired artifacts only with their compatible Runner and migration
   policy. Retain cleanup obligations; an older binary does not process the new
   table and must not be allowed to dispatch over unknown prior writers.

Real local and true remote multi-step completed cycles, provider/effective-model
proof, isolated disturbances and at least 60 minutes of repeated completed cycles
remain acceptance requirements. Static gates, metadata, transport simulation and
an exit code of zero are not substitutes. Agree cycle count, model/resource/cost
budget and isolated target authority before sustained provider calls.

Queue Pause uses the Runner 1.15 control capability: Pages journals queue-only
pause intent; the Runner may seal a never-spawned claim only by winning the
exclusive claim-directory creation. Existing preparing or launched claims drain
normally. The interrupted job remains historical; Resume allocates a new attempt
at the paused frontier. Reconnect replays the same intent. Explicit Stop remains
separate and durable. No absent ownership file establishes process freedom.

Embedded engines with a minimal repository can still handle read-only execution;
writable scheduling requires the concrete repository's atomic reservation and
blocker capabilities and fails closed without them. Logical reset requires the
engine's serialized reset capability; legacy embedded recovery boundaries cannot
silently emulate it. Production wiring provides both concrete aggregates.

Mixed local/remote runs reconcile interrupted local processes at Pages startup
without revoking or restarting the remote jobs. Accepted CLI results from every
supported CLI receive the checkpoint required to preserve completed predecessors.

Local write coordination also compares parent/child canonical directory resources
and a verified shared Git common-directory/branch identity. Distinct worktrees on
the same branch cannot become duplicate writers. Unknown owner evidence retains
a visible obligation. Completed predecessors keep their original execution and
attempt identities when linked into a recovered run.

Control of an own run requires current plan edit permission and verified executor
ownership. Losing read access to historical tickets, models, assets or workspaces
does not disable Stop or reviewed restart/reset. UI and MCP expose only the own
run identity, state and revision needed for those actions in that case. Historical
names, outputs, errors, resource details, sessions and execution history remain
hidden. Pause and Resume still require full current resource access. Unverified
ownership or unexpected server/storage failures never create control authority.
Polling preserves restart, cleanup and writer-wait metadata after refresh.

An isolated restart/permission check also exposed DuckDB 1.5.5 secondary ART
corruption: a normalized role-name index returned zero rows while a scan found
one, and an ordinary role save failed fatally on index deletion. DuckDB's
[upstream shutdown-checkpoint analysis](https://github.com/duckdb/duckdb/pull/23848)
explains how context-free shutdown after WAL replay can serialize unbound indexes
without their buffered entries. This is an identified restart failure, not an
explanation assigned to the historical NAS run.

`Database.close` now queues an explicit CHECKPOINT while the connection is live.
Migration 085 rebuilds the 37 existing explicit secondary indexes under new names
in the ordinary migration transaction. Tables, primary/foreign keys, unique
expressions, plan states, journals, account rights, credentials and user files are
retained. Duplicate data or another rebuild error fails the migration rather than
disabling a constraint. The subsequent normal migration checkpoint persists the
rebuilt structures with an active context. No ad hoc status/index patch is part of
recovery. Existing deployment must be backed up and allow the index-rebuild work
before the separately authorized joint rollout; no production migration was run
for this assignment.
